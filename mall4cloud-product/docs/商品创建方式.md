## 一、结论

### 1、商品主数据的创建入口

当前 `mall4cloud-product` 模块中，商品主数据的创建入口只有一个，即后台管理接口 `POST /admin/spu`。

这里说的商品主数据，指的是以下内容：

- `spu`
- `sku`
- `spu_detail`
- `spu_extension`
- `spu_attr_value`
- `spu_sku_attr_value`
- `sku_stock`

保存入口位于：

- `com.mall4j.cloud.product.controller.admin.SpuController#save`

### 2、不是只能平台 admin 录入

这里的 `admin` 更准确地说是“后台管理端接口前缀”，不是“只能平台管理员录入”。

从现有代码看，商品录入主体主要是商家后台。商家端前端发布商品时，调用的也是商品服务的 `/admin/spu` 接口。

也就是说，当前实现并不是“只有平台 admin 才能创建商品”，而是“只有后台管理端接口可以创建商品”。

### 3、未发现其他商品同步创建渠道

在当前代码范围内，未发现以下渠道会写入商品主数据：

- Feign 内部同步创建商品
- MQ 消费后创建商品
- 定时任务同步商品
- Excel 导入商品
- 初始化 SQL 导入商品
- App 端直接创建商品

结论是：商品主数据创建目前集中在 `/admin/spu` 这一条链路上。

## 二、目录与设计说明

### 1、从项目目录结构看商品模块职责

根据 `mall4cloud目录结构.md` 的说明，`mall4cloud-product` 属于商品服务，负责商品域相关能力，主要包括：

- 分类
- 品牌
- 属性
- SPU
- SKU
- 库存
- 购物车

该模块分层也符合项目的标准结构：

- `controller`：对外提供接口
- `service`：业务逻辑
- `mapper`：数据库访问
- `model`：表结构映射对象
- `dto/vo/bo`：传输对象
- `feign`：内部服务调用
- `listener`：MQ 监听处理

### 2、商品归属的设计方式

从表结构和代码实现看，系统没有单独设计“商品来源”字段，例如 `source` 或 `source_type`。

当前商品归属主要通过 `shop_id` 表达，也就是商品属于哪个店铺。平台商品和商家商品共用一套商品模型，但通过店铺维度做隔离。

因此，这套设计更像是“按店铺归属管理商品”，而不是“存在多个外部系统同步导入商品”。

## 三、商品创建入口分析

### 1、Controller 入口

商品保存入口在：

- `mall4cloud-product/src/main/java/com/mall4j/cloud/product/controller/admin/SpuController.java`

核心接口如下：

```java
@PostMapping
public ServerResponseEntity<Void> save(@Valid @RequestBody SpuDTO spuDTO) {
    checkSaveOrUpdateInfo(spuDTO);
    spuService.save(spuDTO);
    return ServerResponseEntity.success();
}
```

这里可以确认两件事：

- 商品新增入口是 `POST /admin/spu`
- Controller 校验完成后，交给 `spuService.save(spuDTO)` 执行真正保存

### 2、保存调用链

商品创建的主链路如下：

```text
POST /admin/spu
-> SpuController.save
-> SpuServiceImpl.save
-> spuMapper.save
-> spuAttrValueService.saveBatch
-> spuDetailService.save
-> spuExtensionService.save
-> skuService.save
-> skuMapper.saveBatch
-> skuStockMapper.saveBatch
-> spuSkuAttrValueMapper.saveBatch
```

说明如下：

- `SpuServiceImpl.save` 负责保存商品主表和扩展信息
- `SkuServiceImpl.save` 负责批量保存 SKU、库存和销售属性
- SKU 不是单独通过 Controller 创建，而是跟随 `SpuDTO` 一次性提交

### 3、SKU 的创建方式

SKU 数据来自 `SpuDTO.skuList`，也就是发布商品时，由前端一次性把 SPU 和 SKU 信息一起提交给后端。

因此当前系统不是“先创建 SPU，再单独创建 SKU”的模式，而是“创建商品时同时创建 SKU”的模式。

## 四、谁在创建商品

### 1、App 端没有商品创建接口

`controller/app` 下主要是面向 C 端的查询、购物车、库存锁定等接口。

当前没有发现 App 端商品新增接口。

这说明普通用户前台不会直接创建商品。

### 2、Feign 没有商品创建接口

`feign` 目录下存在商品相关内部接口，但当前看到的主要是查询能力，没有发现通过 Feign 写入商品主数据的实现。

这说明其他微服务不会通过内部 Feign 直接创建商品。

### 3、商家后台是主要录入端

结合后端接口结构和前端调用方式，可以判断当前商品的主要录入方是商家后台。

也就是说，商家后台发布商品时，实际调用商品服务后台接口完成落库。

## 五、是否存在其他同步渠道

### 1、MQ Listener 不是商品创建渠道

`listener` 目录下存在两个消息消费者：

- `OrderNotifyStockConsumer`
- `StockUnlockConsumer`

这两个消费者处理的都是库存锁定状态相关逻辑，例如：

- 支付成功后将库存锁定标记为已使用
- 订单关闭后解锁库存

它们处理的是库存，不会新增 `spu` 或 `sku`。

### 2、未发现定时任务创建商品

在当前商品模块中，没有发现以下典型定时任务实现：

- `@Scheduled`
- `@XxlJob`
- 独立 `task` 目录

因此没有证据表明系统会通过定时任务同步创建商品。

### 3、未发现导入逻辑创建商品

当前没有发现明显的商品导入能力，例如：

- Excel 导入
- EasyExcel 监听导入
- 批量导入商品 Service

因此没有证据表明系统支持通过导入方式批量创建商品。

### 4、数据库初始化脚本不是商品来源

`db/mall4cloud_product.sql` 主要是建表脚本，没有看到初始化插入大量商品数据的逻辑。

因此数据库脚本也不是当前商品创建来源。

## 六、需要避免的误判

### 1、商品模块内有其他写库行为

虽然没有发现其他“商品主数据创建渠道”，但商品模块内部确实存在其他写库行为，例如：

- 品牌新增、修改、删除
- 购物车写入
- 库存锁定与释放

这些写库行为都发生在 `mall4cloud-product` 模块里，但它们不属于商品主数据创建。

### 2、库存相关写入不等于商品同步

订单、支付、库存锁定相关逻辑会更新以下数据：

- `sku_stock`
- `sku_stock_lock`
- 相关状态字段

这些属于交易过程中的库存变更，不应理解为“有其他渠道同步创建商品”。

## 七、最终判断

### 1、关于商品来源

当前系统里，商品主数据的来源可以概括为：

- 通过后台管理端接口创建
- 主要由商家后台录入
- 以店铺 `shop_id` 作为商品归属维度

### 2、关于保存方式

当前商品保存方式是：

- 通过 `POST /admin/spu` 统一提交
- 在 `SpuServiceImpl.save` 中事务化保存 SPU、SKU、详情、扩展、属性、库存等信息

### 3、关于是否有其他同步渠道

当前分析范围内，没有发现除 `/admin/spu` 之外的商品主数据创建或同步渠道。

可以认为目前商品创建方式是单入口模式。
